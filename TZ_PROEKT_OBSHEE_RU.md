# Техническое задание (общее описание проекта)

**Проект:** crgtransp72app  
**Платформа:** Flutter (Dart SDK ≥ 3.3.4)  
**Версия приложения (pubspec):** 3.0.2+4  

Документ описывает назначение продукта, роли пользователей, архитектуру экранов и правила разработки. Детальная карта экранов по веткам: [BRANCH_SCREENS_MAP_RU.md](./BRANCH_SCREENS_MAP_RU.md).

---

## 1. Назначение

Мобильное приложение для рынка транспортных и смежных услуг (грузоперевозки, спецтехника, грузчики). Две основные роли:

- **Заказчик** — ищет исполнителей, публикует заказы, ведёт заявки и профиль в своей ветке интерфейса.
- **Грузоперевозчик (исполнитель)** — просматривает объявления заказчиков, откликается, ведёт заявки и профиль в отдельной ветке.

Серверная логика и данные доступны через HTTP API (базовый URL задаётся в `lib/config.dart`).

| Роль | Точка входа в UI | Основной «корневой» экран |
|------|------------------|---------------------------|
| Заказчик | Выбор «Я заказчик» | `lib/pages/zakaz_screen1.dart` (`MyApp` / `MyCustomScreen`) |

Стартовый поток приложения: `lib/main.dart` → `start_pages.dart` (выбор роли и далее переход в соответствующую ветку).

## 4. Архитектура веток (критично для ТЗ)

### 4.1. Принцип разделения

У заказчика и исполнителя **разные файлы** для схожих по смыслу экранов (например, «список городов», «услуги/техника»). **Нельзя** подставлять экраны и нижнее меню одной ветки в другую.

### 4.2. Нижняя навигация

- Заказчик: `lib/pages/customer_bottom_nav.dart` (`CustomerBottomNav`).
- Исполнитель: `lib/pages/performer_bottom_nav.dart` (`PerformerBottomNav`).

Параметры вида `showBottomNav`, `useCustomerNavigation`, `useCustomerMenu`, `embedInCustomerShell` на отдельных экранах должны согласовываться с оболочкой, чтобы **не дублировать** два `BottomNavigationBar` и не показывать меню «чужой» роли.

### 4.3. Соответствие «услуги / города / ленты» (кратко)

| Ветка | Каталог услуг/техники | Список городов | Дальнейший контент |
|--------|------------------------|----------------|---------------------|
| Заказчик | `get_vt_z.dart` (`MyImageGrid`, при встраивании в shell — `MyAppI1zPage`) | `CityScreenisp.dart` → API `get_citiesisp.php`; на экране списка городов — **`CustomerBottomNav`** (вкладка «Услуги») | `outputob.dart` (исполнители), меню заказчика |
| Исполнитель | `get_vt.dart` (`MyImageGrid`) | `CityScreen.dart` → API `get_cities.php`; на экране — **`PerformerBottomNav`** | `outputobz.dart` (объявления заказчиков), меню исполнителя |

Подробная таблица, обходные экраны грузоперевозчика (`history_isp`, `outputobzlikes1`, `bmenu`, `scrmenu`) и проверочный чеклист: [BRANCH_SCREENS_MAP_RU.md](./BRANCH_SCREENS_MAP_RU.md).

### 4.4. Меню заказчика в обходном сценарии (`MenuzakScreen`)

В `lib/pages/menuzak.dart` первая вкладка «Услуги» должна использовать **заказческий** экран из `get_vt_z.dart` (`MyAppI1zPage`), а не сетку из `get_vt.dart` (ветка исполнителя), иначе открывается неверный список городов и цепочка API.

## 5. Ключевые функциональные блоки (без исчерпывающего перечня файлов)

1. **Авторизация / токен** — работа с сервером через токен (`getuserinfo.php` и др.), диалоги «требуется авторизация» на защищённых действиях.
2. **Каталоги и города** — загрузка изображений категорий, выбор города, переход к спискам объявлений/исполнителей в зависимости от роли.
3. **Объявления и отклики** — карточки, лайки, телефоны, экраны предложений (`OfferScreen`, `OfferScreen2` и др.) с учётом роли и нижнего меню.
4. **Профиль и «мои объявления»** — `ads1.dart` / `ads2.dart`, редактирование форм (`edit_ob_*.dart`, `add_ob_*.dart`), согласованное обновление списка после удаления/редактирования без лишних вложенных `MaterialApp`.
5. **Заявки и исполнение заказа** — отдельные экраны для заказчика и исполнителя, подсветка вкладок в нижнем меню при активных заявках (запросы к API статуса заказа).
6. **Push** — FCM, отправка уведомлений с сервера, интеграция в формах отклика/предложений (см. соответствующие `notification.php` и клиентский код).

## 6. Требования к качеству и регрессии

1. Перед релизом прогонять сценарии **полностью** для заказчика и для исполнителя (см. раздел «Проверка перед релизом» в `BRANCH_SCREENS_MAP_RU.md`).
2. При добавлении нового экрана с нижним меню явно указывать ветку (`CustomerBottomNav` vs `PerformerBottomNav`) и параметры встраивания в существующий `Scaffold`.
3. Избегать вложенного `MaterialApp` внутри уже показанного дерева приложения без необходимости; для вкладки «Услуги» заказчика использовать виджет страницы без второго `MaterialApp` (`MyAppI1zPage`).
4. Поля из API с нестабильным типом (строка vs число) приводить к целевому типу перед сравнением в UI (рейтинги, счётчики и т.п.).
