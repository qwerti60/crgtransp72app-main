## 1. Роли и изоляция данных

- Один `users.idusers` может быть **заказчиком** и **исполнителем** одновременно.
- Роль в операции определяется **контекстом сделки**, не полем профиля.
- Ключ объявления всегда **`(bd, id)`**, не только `id` — id может совпадать в `orders`, `orderst`, `ordersg`, `add_ob_*`.
- **Dual-role:** в роли заказчика пользователь **не видит свои объявления исполнителя** (supply), в роли исполнителя — **не видит свои заявки заказчика** (demand). Фильтр `a.iduser != viewer_id` обязателен; без `useId` выдача supply **пустая** (`api/include/viewer_user.php`).
- В «Заявки» заказчика (`zprofil_zakaz`) не показываются карточки, где `a.iduser = id заказчика` (свои объявления исполнителя, на которые случайно оставлен `offer_dataf`).

## 2. Два сценария сделки

### 2.1. Сценарий 1 — исполнитель → заявка заказчика

| Шаг | Кто | Действие | API / экран |
|-----|-----|----------|-------------|
| 1 | Исполнитель | «Предложить услуги» | `OfferScreen` → `add_offer.php` → `offer_data` |
| 2 | Заказчик | «Предложения исполнителей» | `list_predloj_na_obj_isp` → `list_predloj_na_obj_isp_new.php` |
| 3 | Заказчик | Принять одного (`isp=1`) | `updatePriemZak.php` + `source=customer_order` |
| 4 | Исполнитель | «Начать выполнение» | `check_order_status.php` + `source=customer_order` → `ordersglobal` |
| 5 | Обе стороны | Таймер, чат, завершение | `OrderExecutionScreen*` |
| 6 | Обе стороны | Отзывы | `save_review*.php`, формы на экране выполнения |

**Таблица:** `offer_data` — `iduserp` = исполнитель, `iduser` = id **заявки** заказчика, `bd` = 1/2/3.

**После принятия (сценарий 1):**

- Заявка **скрыта от всех исполнителей** в поиске (`getads3.php`, `search_services_core.php`).
- У **принятого** исполнителя заявка **остаётся** в «Предложения» (`getofferusern_new.php` — `status IN (0,1)`) с кнопкой «Начать выполнение».
- Другим исполнителям в списке откликов: **«Исполнитель уже выбран»**, кнопка «Принять» неактивна (см. §4).

**После отказа заказчиком от предложения (`status=2` в `offer_data`):**

- Предложение **не удаляется** из БД — остаётся со статусом «отказано» (строку **не** DELETE; см. промпт «строку offer_data нужно удалять» → согласовано: **сохранять** для истории и блокировки повтора).
- У **заказчика** на экране «Предложения исполнителей» отказанное предложение **исчезает** из списка.
- У **исполнителя** в «Предложения» (`zprofil_zayavki`) — баннер **«Заказчик отказался от вашего предложения»**.
- Редактирование / повторное предложение / старт выполнения **скрыты**; удаление отклика **доступно**.
- Повторный отклик на то же объявление блокируется API (`add_offer.php` при `status=2`).

### 2.2. Сценарий 2 — заказчик → объявление исполнителя

| Шаг | Кто | Действие | API / экран |
|-----|-----|----------|-------------|
| 1 | Заказчик | «Предложить заказ» | `OfferScreen2` → `add_offerzakaz.php` → `offer_dataf` |
| 2 | Исполнитель | «Заявки на объявление» | `list_predloj_na_zayavki` |
| 3 | Исполнитель | Принять (`isp=1`) | `updatePriemZak.php` + `source=performer_ad` |
| 4 | Исполнитель | «Начать выполнение» | `check_order_status.php` + `source=performer_ad` |
| 5 | Завершение | Отзывы, история | как в сценарии 1 |

**Таблица:** `offer_dataf` — `iduserp` = заказчик, `iduser` = id **объявления** исполнителя.

**Скрытие в поиске (сценарий 2 — по согласованию):**

- Объявление исполнителя **остаётся в общей выдаче** для других заказчиков.
- На время **активной** сделки (`ordersglobal.status = 'выполняется'`) — скрыто **только от участника** этой сделки (или блок повторного оффера через `check_offer_zakaz.php`).
- После **выполнения** тот же заказчик **может снова** предложить заказ на то же объявление.

**Объявление исполнителя на модерации (`flag = 0`):** не показывается заказчику в поиске (`get_ads2_new.php`, `search_services_core.php`).

## 3. Выполнение заказа и таймер

### 3.1. Старт выполнения

- Исполнитель нажимает **«Начать выполнение»** (`zprofil_zayavki` → вкладка «Заявки» shell исполнителя).
- Сервер создаёт/возобновляет запись `ordersglobal` со статусом `выполняется`, поле `start_time` в формате MySQL `Y-m-d H:i:s` (`api/include/datetime_mysql.php`).
- Push заказчику: «Исполнитель начал выполнение вашего заказа!».

### 3.2. Экраны таймера

| Роль | Экран | Shell |
|------|-------|-------|
| Исполнитель | `OrderExecutionScreen.dart` | `zakaz_screen2`, вкладка «Заявки» |
| Заказчик | `OrderExecutionScreenzak.dart` | `zakaz_screen1`, вкладка «Заказы» |

**Правила таймера:**

- Время считается от `start_time` в `ordersglobal` (синхронизация при открытии экрана через POST `check_order_status.php` / `check_order_statusisp2.php`).
- Цифры таймера — **компактные** (~26px), не `displayMedium`.
- При некорректном `start_time` в БД — fallback на `DateTime.now()`, таймер всё равно стартует.

### 3.3. Навигация заказчика к таймеру

Заказчик должен попадать на **счётчик / экран выполнения**, если:

- заказ **выполняется** (`ordersglobal.status = 'выполняется'`), или
- заказ **выполнен**, но заказчик **не оставил отзыв** об исполнителе (`needs_review: true` в `check_order_statusisp.php`).

После сохранения отзыва вкладка «Заказы» снова показывает **поиск исполнителей**; отзыв можно **изменить** с экрана выполнения, пока открыт завершённый заказ (кнопка «Изменить отзыв о исполнителе»).

**Точки входа:**

| Действие | Поведение |
|----------|-----------|
| Вкладка **«Заказы»** в нижнем меню | Всегда → `MyApp(initialPage: 1)` → экран выполнения при активной сделке |
| **«Мои объявления»** в профиле | Если активная сделка / нет отзыва → счётчик; иначе → список объявлений (`customer_orders_hub_nav.dart`) |
| Автовход в приложение | При `hasActiveOrder` автопереход на вкладку «Заказы» (как у исполнителя) |

Красная иконка вкладки «Заказы» / «Заявки» только при **`выполняется`** или **`needs_review`** (не при уже оставленном отзыве).

### 3.4. Отзывы после завершения

| Роль | Таблица | Кто пишет | Поля в БД | Форма |
|------|---------|-----------|-----------|-------|
| Исполнитель → о заказчике | `reviews` | исполнитель | `user_id` = исполнитель, `target_user_id` = заказчик | `SendReviewForm.dart` |
| Заказчик → об исполнителе | `reviewsisp` | заказчик | `user_id` = **исполнитель** (о ком отзыв), `target_user_id` = **заказчик** (автор) | `SendReviewFormzakaz.dart` |

**Правила (симметрично для обеих сторон):**

- После **«Завершить заказ»** на экране выполнения — кнопка **«Оставьте отзыв»** / **«Изменить отзыв»** (`_hasExistingReview` через `get_review_between.php`).
- При первом контакте с контрагентом — **новый** отзыв; при повторной работе — **редактирование** существующего (`save_review.php` / `save_reviewzaka.php` — UPDATE по паре).
- Заказчик: диалог после завершения с кнопками **«Оставить отзыв»** / **«Позже»**; API проверки активной сделки — `check_order_statusisp.php` (поля `needs_review`, `has_review`, `status`).
- Исполнитель: блокировка **нового** «Начать выполнение», пока есть другой заказ `выполняется` или нет отзыва о заказчике по завершённому — `api/include/performer_order_gate.php` + `check_order_status.php`.

### 3.5. Блокировка нового «Начать выполнение» (исполнитель)

Исполнитель **не может** начать выполнение **другого** заказа, если:

1. Уже выполняется **иная** сделка (`ordersglobal.status = 'выполняется'` для другого `order_id` / `user_idok`).
2. Есть **завершённый** заказ **без отзыва** о заказчике в таблице `reviews` (проверка в `performer_order_gate.php`).

**Где блокируется:**

| Место | Поведение |
|-------|-----------|
| `zprofil_zayavki.dart` | Кнопка серая / баннер; текст «Завершите текущий заказ» / «Сначала оставьте отзыв» |
| `list_predloj_na_zayavki.dart` | То же на экране «Предложения заказчиков» на объявлении |
| `check_order_status.php` | Сервер отклоняет INSERT в `ordersglobal` (`blocked: true`) |

Продолжить **текущую** сделку (тот же `order_id` + заказчик) можно — это возобновление таймера, не новый старт.

### 3.6. Завершение и отмена

- **Завершить** / **Отказаться** → `update_order_status.php` → статус `выполнен` / `отменен`.
- После завершения — форма отзыва на экране выполнения (см. §3.4).

### 3.7. История сделок

- Завершённые (`выполнен`) и отменённые (`отменен`) сделки попадают в **историю** заказчика и исполнителя (`list_history_zak.php`, `list_history_isp.php`).
- История сохраняется при **удалении** объявления заказчиком из «Мои объявления» (§5).
- Поле `deal_source` в `ordersglobal` различает сценарии 1 и 2.

## 4. «Мои объявления» заказчика после выполнения

**Экран:** `ads2.dart` (`Ads2Page` / `Ads2Shell`), API: `zak_get_ads.php`, модуль `api/include/customer_order_deal.php`.

| Состояние | UI |
|-----------|-----|
| `order_status = выполнен` | Плашка **«Выполнено · объявление неактивно»**, карточка приглушена |
| `order_status = выполняется` | Плашка **«Заказ выполняется · объявление неактивно»** |
| Неактивно | Редактирование отключено; кнопка откликов скрыта; **удалить** можно (с сохранением истории) |

**Поиск:** объявления с `ordersglobal.status IN ('выполняется', 'выполнен')` **не показываются** исполнителям (`getads3.php`, `search_services_core.php`).

**Исполнители с откликами** (`getofferusern_new.php`, `zprofil_zayavki.dart`):

- Заявка **остаётся** в «Предложения» с полями `order_status`, `chosen_performer_id`.
- Если выбран **другой** исполнитель → баннер **«Исполнитель уже выбран»**, без кнопок редактирования/старта.
- Если выбран **этот** исполнитель и заказ выполнен → **«Заказ выполнен»**.

**Кнопка счётчика откликов** на карточке — **круглая** (CircleBorder, ~42×42), не прямоугольная.

## 5. Удаление объявления и история

**Проблема (исправлено):** удаление ломало историю, если чистились все `offer_data`.

**Правила `delete_zakaz.php`:**

- Удалять объявление только из таблицы по **`bd`** (1=`orders`, 2=`orderst`, 3=`ordersg`).
- Из `offer_data` удалять только **непринятые** (`status = 0`).
- Строки с **`status = 1`** и записи **`ordersglobal`** сохранять для истории.

История: `list_history_zak.php`, `list_history_isp.php` — UNION сценариев 1 и 2, поле `deal_source`.

## 6. Навигация и нижнее меню

### 6.1. Общие правила

- **Не смешивать** `CustomerBottomNav` и `PerformerBottomNav`.
- **Не вкладывать** лишний `MaterialApp` в shell — иначе меню пропадает после `Navigator.push`.
- Редактирование «Мои объявления» — во **вложенном Navigator** (`Ads1Shell`, `Ads2Shell`, `MenuzakScreen`, `HistortScreen`).
- Экраны **выполнения заказа** и **чат по сделке** — **без** нижнего меню (`showBottomNav: false`, `rootNavigator: true` для чата).

### 6.2. «Мои объявления» и редактирование

| Роль | Shell | Меню при редактировании |
|------|-------|-------------------------|
| Заказчик | `Ads2Shell` / `MenuzakScreen` | `CustomerBottomNav` остаётся |
| Исполнитель | `Ads1Shell` / `HistortScreen` | `PerformerBottomNav` остаётся |

После сохранения — `Navigator.pop` во вложенный navigator, не новый `MaterialApp`.

### 6.3. Поиск и «Найти исполнителей / заявки»

| Действие | Заказчик | Исполнитель |
|----------|----------|-------------|
| Вкладка поиска | «Заказы» → `SearchFormisp` / `CustomerSearchScreen` | «Заявки» → `SearchForm` / `PerformerSearchScreen` |
| Быстрый подбор с карточки «Мои объявления» | «Найти исполнителей» → `openPerformersForCustomerAd` | «Найти заявки» → `openOrdersForPerformerAd` |
| Пустой результат из профиля | Открыть **полный экран поиска** (`openSearchOnEmpty`) | То же |

**Нижнее меню (важно):**

- Экран открыт **внутри shell** (`MenuzakScreen`, `Ads2Page`, `MyApp` с `embedInCustomerShell: true`) → дочерние `outputob` / `CustomerSearchScreen` с **`showBottomNav: false`** — одно меню снаружи.
- Кнопка «Найти исполнителей» в `ads2.dart` передаёт `embedInShell: !showBottomNav` в `ad_match.dart`.
- Отдельный push с корневым меню — только если экран открыт **вне** shell (`showBottomNav: true`).

Счётчики `(N)` в выпадающих списках поиска: `api/search_order_counts.php` — только при переданном `useId`; для заказчика supply, для исполнителя demand.

### 6.5. Сохранение роли при повторном входе

- Если на устройстве последней была роль **исполнителя** — при открытии приложения стартовать в ветке исполнителя (вкладка «Объявления» / «Техника»).
- Если последней была роль **заказчика** — стартовать в ветке заказчика (вкладка «Услуги»).
- Реализация: сохранение выбора роли в локальном хранилище при входе в `zakaz_screen1` / `zakaz_screen2`.

### 6.6. Экраны без нижнего меню (полный список)

| Экран | Условие |
|-------|---------|
| `OrderExecutionScreen` / `OrderExecutionScreenzak` | всегда |
| `ChatThreadScreen` с таймера, карточек, иконки 💬 | `showBottomNav: false`, `rootNavigator: true` |
| `SupportComposeScreen`, чат поддержки | без меню |
| `OfferScreen` из `outputobz` («Предложить услуги») | без **двойного** меню |
| `OfferScreen2` | без кнопок «Написать» на форме; без двойного меню |
| `list_predloj_na_obj_isp` (предложения заказчика) | без меню при открытии из карточки |
| `zprofil_zayavki` (предложения исполнителя) | без меню при открытии из карточки |

**Редактирование «Мои объявления»** — меню **должно** оставаться (`Ads1Shell`, `Ads2Shell`, `MenuzakScreen`, `HistortScreen`).

## 7. Поиск услуг и заказов

Подробно: [search_logic_ru.md](./search_logic_ru.md).

| Кто | Куда | Что ищет | API |
|-----|------|----------|-----|
| Заказчик | «Заказы» | Исполнителя | `search_services.php` role=customer, fallback `get_ads2_new.php` |
| Исполнитель | «Заявки» | Заказ | `search_services.php` role=performer, fallback `getads3.php` |
| Счётчики в форме | оба | `(N)` у городов/услуг | `search_order_counts.php` |

**Исключения supply (заказчик ищет исполнителя):**

- Свои объявления исполнителя (`iduser = viewer`, обязателен `useId` > 0).
- `(flag IS NULL OR flag = 1)` — не на модерации.
- Сделка `выполняется` с этим заказчиком (`ordersglobal` + `offer_dataf`).
- Категория «Грузчики»: таблица `add_ob_gr`, разрешение категории как в `get_ads2_new.php` (`search_resolve_supply_category`).

**Исключения demand (исполнитель ищет заказ):**

- Свои заявки.
- `enddatez` просрочен.
- Есть принятый отклик (`offer_data.isp = 1`).
- Сделка в `ordersglobal` со статусом **`выполняется`** или **`выполнен`**.

**Свободный текст:** строка вида «экскаватор в Тюмени» — парсинг города и категории на сервере (`search_services_core.php`).

**Модерация исполнителя:** `(flag IS NULL OR flag = 1)` в supply-поиске.

## 9. Чаты

Подробно: [chat_logic_ru.md](./chat_logic_ru.md).

### 9.1. Типы

| Тип | Участники | Где |
|-----|-----------|-----|
| `deal` | Заказчик ↔ исполнитель | По сделке, иконка 💬 у телефона на карточках |
| `support` | Пользователь ↔ оператор | Профиль → «Поддержка»; admin-web |

### 9.2. Правила доступа

- Написать можно **только после авторизации** (`ensureChatAuthorized`).
- Чат по сделке создаётся при старте выполнения (`crg_chat_on_ordersglobal_created`).
- С экранов **таймера** и карточек — чат **без нижнего меню** (`showBottomNav: false`, `rootNavigator: true`).

### 9.3. Точки входа deal-чата

- Иконка чата рядом с телефоном на карточках (`outputob`, `outputobz`, списки предложений).
- Кнопка «Чат по заказу» на `OrderExecutionScreen` / `OrderExecutionScreenzak`.
- Профиль → «Чаты с исполнителями» / «Чаты с заказчиками» + «Поддержка».

### 9.4. Вложения

- Изображения и документы в чате (`chat/send.php`, `crg_chat_process_upload`).
- Просмотр вложений в admin-web (`support_attachment.php`).

### 9.6. Техподдержка и admin-web (реализовано)

## 14. Чек-лист регрессии (краткий)

### Сценарий 1

- [ ] B видит заявку A; A не видит свою в поиске
- [ ] B откликается; A принимает → `offer_data.isp=1`
- [ ] C (другой исполнитель) видит «Исполнитель уже выбран»
- [ ] B начинает выполнение → таймер у обоих, чат без меню
- [ ] Заявка скрыта из поиска исполнителей
- [ ] После завершения — отзыв, в «Мои объявления» A: «Выполнено · неактивно»
- [ ] Удаление объявления A **не** стирает историю
- [ ] Отказ A от отклика B → B видит отказ, не может редактировать/стартовать

### Сценарий 2

- [ ] A предлагает заказ на объявление B; B принимает
- [ ] Объявление B видно другим заказчикам; скрыто от A на время выполнения
- [ ] После выполнения A может снова предложить заказ
- [ ] Объявление B с `flag=0` не видно в поиске

### Навигация

- [ ] «Мои объявления» + редактирование — меню на месте (обе роли)
- [ ] Заказчик с активной сделкой: «Заказы» и «Мои объявления» → счётчик
- [ ] Чат с таймера — fullscreen без tab bar

### Dual-role

- [ ] UserD = заказчик + исполнитель: в роли заказчика **не видит** свои `add_ob_*` в поиске и «Заявки»
- [ ] UserD в роли исполнителя **не видит** свои `orders*` в поиске заявок
- [ ] Данные не смешиваются в истории и «Мои объявления»

### Отзывы и старт выполнения

- [ ] После завершения заказчик видит кнопку отзыва; первый раз — «Оставьте», повторно — «Изменить»
- [ ] Исполнитель без отзыва о заказчике не может «Начать выполнение» другого заказа
- [ ] Исполнитель с заказом `выполняется` не может стартовать другой (кроме продолжения текущего)

### Навигация поиска

- [ ] «Найти исполнителей» из «Мои объявления» в профиле — **одно** нижнее меню
- [ ] Счётчики `(N)` совпадают с результатами поиска при том же `useId`
